# Divini Partners — Role-Based Subscriptions, Business Operating System, and Procurement Moat

## Architecture & Implementation Audit

Status: **DRAFT FOR REVIEW — no implementation has started.** Per the project's own rule ("do not begin major implementation until the audit is complete"), this document is the checkpoint. Everything below is verified against the actual code and a live-database schema dump, not inferred from documentation or comments alone — several places where the docs/comments say one thing and the code does another are called out explicitly.

Last updated: 2026-08-03

---

## 0. Executive summary

The good news: this codebase already has real, *partially* centralized fee logic (`server/src/lib/platformFees.ts` plus the legacy `TIERS` constant in `server/src/db.ts`) that matches the spec's numbers almost exactly — Free/Partner/Premier at 5%/2.5%/1%, and a genuine, correctly-implemented **$2,500-per-event cumulative cap** — but, verified precisely below, that cap is only actually enforced in one of the two places money gets priced (the quote/invoice pricing path, `db/quotes.ts`'s `clientPlatformFee`), not the other (the direct payment-recording path, `db/payments.ts`'s `computeFees`, which is what the live-verified Stripe checkout-capture flow from earlier this session actually calls). There is also a genuinely excellent existing example of tier-gated feature access already shipped and enforced server-side — Premier-only Contract Pricing (`routes/contracts.ts`) — plus a substantial, currently-**live** tier-based marketplace-access mechanism (bid visibility windows, `db/bids.ts`) that already does exactly what the spec asks for ("more lead-generation capabilities" as an upgrade trigger). These are real, reusable patterns — not "start from nothing."

The headline gap, confirmed by direct code inspection, not guesswork: **there is no recurring billing anywhere in this application.** Not for the $45/$99 tier prices, not for team seats, not for Featured Vendor placement. All three "subscription-shaped" concepts are a status flag on a row with, at most, an optional *one-time* Stripe Checkout Session a user can manually trigger — and Featured Vendor doesn't even go that far: `buyFeatured()` never calls Stripe or PayPal at all, under any configuration; it takes a client-submitted `processor_ref` string, doesn't validate it against anything, and marks the org featured for a month regardless. Nothing charges monthly. Nothing renews automatically. Nothing downgrades a lapsed account. A user can currently self-select `tier: "premier"` at registration and get the 1% fee rate for free, forever — the field is accepted from the client with no payment check at all, and the *only* code path anywhere that changes an org's tier after registration is a super-admin manually promoting an org to white-label. One direct consequence worth knowing before anyone looks at a dashboard: the admin Revenue Center's reported MRR/ARR is computed purely by summing `$45`/`$99` for every org whose self-declared `tier` is partner/premier — it is not connected to any actual charge and should not be treated as real revenue until Phase 1 ships. This is the single most consequential finding in this audit: "preserve the existing Free/Plus/Pro structure" cannot mean "leave the billing enforcement as-is," because there is no billing enforcement to preserve. The *fee math* is mostly real; the *subscription* is not.

Worth noting in the "reuse, don't reinvent naming" spirit of the spec's own rules: **"Plus" and "Pro" are not new names to introduce** — they already exist, verbatim, in `src/pages/GetStarted.tsx`'s client-facing tier picker (`{ key: 'partner', label: 'Plus', price: '$45 / month', fee: '2.5% fee, capped $2,500/event' }` / `{ key: 'premier', label: 'Pro', ... }`), just not used consistently elsewhere (the backend `TIERS` labels say "Partner"/"Premier," and the public marketing page shows neither because it markets the tierless Pricing V2 model instead — see §1.7).

Second headline gap: the spec requires a user to belong to **one or more** organizations (a planner who also owns a venue, a sponsor agency managing multiple brands). The current schema is **single-org-per-user** end to end — `users.organization_id` is one foreign key, `getActor()` resolves exactly one org, the SPA's auth context holds one `company`, and every dashboard, every route guard, every entitlement check that will be built on top of this assumes it. Building real multi-org membership is a genuine, non-trivial schema addition, not a config change.

Third: there is currently **no usage/quota system of any kind** — no limit on events, quotes, seats, locations, or anything else, on any tier. `organizations.included_seats`/`additional_seats` look like they should be that system but are dead columns — set once at registration and never read or written again anywhere in the server; real seat counting happens in the separate `team_seats` table, disconnected from those two columns and from any cap. This is a blank slate, which is good (nothing to migrate around) but means every limit in the new entitlement system is new logic, not a tightening of existing logic.

Fourth: authorization today is **flat and global**, not scoped. `requireAdmin` is a single email allowlist (`ADMIN_ALLOWED_EMAILS`) with no granular permissions, no per-org admin, no billing-vs-content distinction — and a second, independently-checked admin concept (`users.role IN ('admin','super_admin')`) exists in parallel, re-implemented as a near-identical inline helper function in roughly 40 different `server/src/db/*.ts` files rather than one shared primitive. Role itself has a similar duplication problem: `organizations.type` and `users.role` are two separately-writable copies of "what kind of account is this" that different files fall back on differently when one is null. Both are worth unifying as part of building the new entitlement service, since the entitlement checks will need exactly one reliable source for "who is this and what org are they acting as."

Fourth: the existing global feature-flag system (`src/lib/features.tsx`, `AdminFeatures.tsx`) is currently **non-functional** — the frontend calls `GET /feature-flags`, and no such route exists anywhere on the server. Every flag silently evaluates to "off" for everyone. This is unrelated to subscription entitlements (it's a stage-rollout toggle, not a plan-gate) but it's broken and worth knowing before anyone assumes it does something.

Fifth: the **public pricing page already markets Pricing V2** (flat 5%, no tiers, $10 seats, $49 Featured Vendor — explicitly labeled as such in its own header comment) while the **live backend still runs the legacy tiered model** (`PRICING_V2` flag is off in production per `AI_PROJECT_OS/10_CURRENT_STATE.md`). A decision is needed on which model the new role-based subscription system extends — see §7.

None of this is a criticism of prior work; the fee-cap engine, the Connect payout rails, and the auth/org skeleton are genuinely solid foundations. It means "Phase 1" of this project is necessarily "build real recurring billing + multi-org membership" before any of the seven role-specific operating-system modules can sit on top of real entitlements.

## 1. Current architecture (as it exists today)

### 1.1 Authentication

- Native email/password (`server/src/auth.ts`, `server/src/routes/auth-native.ts`). Sessions are HS256 JWTs (`jose`) signed with `SESSION_SECRET`, delivered as an httpOnly cookie (`divini_session`) and returned in the response body for bearer use. 30-day expiry.
- Email verification is required before login; registration creates an unverified user with a 32-byte hex token.
- `getAuth(req)` returns `{ userId, email, isAdmin, claims }`. `isAdmin` is computed from `ADMIN_ALLOWED_EMAILS` (an env-var allowlist), not a database role — there is exactly one admin tier today, no granular permission scopes.
- No OIDC/Authentik in the live path (fully retired; some dead `OIDC_*` config constants remain, unused, low-priority cleanup).

### 1.2 User / Organization / Role model

- `users` (id, oidc_sub, email, name, phone, **role** text CHECK against a *smaller* enum than the app-level `Role` type — see §6.1 finding, **organization_id** uuid → organizations, account_type, status, notification_preferences).
- `organizations` (id, name, **type** text — free-text, holds the "role" like `venue`/`vendor`/`planner`/etc, no CHECK constraint, **tier** text CHECK in `('client','free_partner','partner','premier','white_label')`, **subscription_status** text, **platform_fee_rate** numeric, **included_seats** int default 1, **additional_seats** int default 0, billing_contact, verification_status, white_label_status).
- **One user → one organization.** `users.organization_id` is a single FK, not a join table. `db.ts`'s `getActor(idOrSub, email)` calls `ensureUser` then `getMyOrg(user.id)`, which does `select o.* from organizations o join users u on u.organization_id = o.id where u.id = $1` — structurally cannot return more than one org. The SPA mirrors this: `src/lib/auth.tsx`'s `MeResponse` has `company: Company | null` (singular), populated from `GET /me`.
- `server/src/db.ts` `Role` type (app-level, used for registration/UI): `venue | vendor | supplier | installer | planner | client | sponsor | billing | nonprofit | donor | volunteer | exhibitor | viewer` (12 values). The **spec's 7 roles** map onto a subset of these: Client→`client`, Venue/Hotel→`venue`, Vendor/Service Provider→`vendor` (and arguably `supplier`), Supplier/Rentals→`supplier`, Event Planner→`planner`, Installer/Support→`installer`, Sponsor/Brand→`sponsor`. `nonprofit`/`donor`/`volunteer`/`exhibitor`/`viewer` are additional roles outside the spec's 7 that already exist and have their own dashboard/registration defaults (see `roleDefaultTier` in `registerOrganization`) — the new entitlement system needs to either fold these into the 7-role model or explicitly carry them alongside it; recommend the latter (do not delete working roles).
- 8 live role dashboards in `src/pages/dashboards/`: Client, Venue, Vendor, Planner, Installer, Sponsor, Nonprofit, SuperAdmin — each a flat, hardcoded `NavItem[]` array with no tier-based hiding today (every nav item is visible regardless of tier; some items point at real routes, a few intentionally stay inert with no `to` when there's no route yet).

### 1.3 Tiers and the fee-cap engine — two implementations, only one of which is capped where it matters most

- Legacy tier system (currently **live** in production; `PRICING_V2=false`): `server/src/db.ts` — `Tier = "client" | "free_partner" | "partner" | "premier"`, with a `TIERS` record carrying `{label, monthly, feeRate}`: free_partner $0/5%, partner $45/2.5%, premier $99/1%. `client` tier is $0/0% (bookers pay no platform fee — the fee is charged to the party *receiving* payment, matching the spec's rule). **This raw `TIERS[tier].feeRate` is what's actually used, uncapped, by `db/quotes.ts` (quote/invoice fee generation), `db/invoices.ts`, `db/payments.ts`'s `computeFees()` (direct payment recording — the function the live-verified Stripe checkout-capture flow from earlier this session calls), `routes/changeorders.ts`, and `routes/autoquote.ts`.**
- A second, separate implementation, `server/src/lib/platformFees.ts` (`computePlatformFee`/`planForOrg`/`PLANS`), *does* correctly cap every plan (including enterprise, unless overridden) at $2,500 (`capCents: 250000`) — but it is only actually called from two places: `routes/fees.ts`'s `/api/fees/preview` (a transparency/preview endpoint, not a real transaction), and `routes/revenue-center.ts` (admin reporting). **It does not gate what a real payment is actually charged.**
- **The $2,500 cap genuinely IS enforced correctly in one real place**: `db/quotes.ts`'s `clientPlatformFee()` (used when a quote is generated or accepted, `quotes.ts:316,359`) implements a proper **per-event cumulative** cap — `EVENT_FEE_CAP_CENTS = 250000; // $2,500 per event, all tiers` — summing every already-accepted/converted quote's fee on that event and capping the new fee to whatever headroom remains, with a $2 floor. This is a well-built, correct implementation of exactly what the spec describes, and it independently confirms the "capped at $2,500 per event, not per transaction" reading is the intended semantics here (not a per-single-payment cap) — worth confirming with the business owner that this is indeed what "capped at $2,500 per event" should mean going forward, since it's a meaningfully different (better, from the vendor's perspective) guarantee than a per-transaction cap.
- **The gap**: `db/payments.ts`'s `computeFees()` — the function actually invoked when a *payment* (as opposed to a quote) is recorded, including the real Stripe checkout-capture path already verified live this session — has **no cap logic of any kind**. A large payment recorded directly (rather than flowing through an already-capped quote/invoice first) is charged the raw uncapped percentage. Whether this is reachable in practice depends on whether every real payment is always preceded by a capped quote/invoice in the current UI flows — that needs verifying against the actual booking flows before Phase 1, since it's exactly the kind of inconsistency a centralized entitlement service is supposed to eliminate.
- Legacy tier fee rates are duplicated between `server/src/db.ts`'s `TIERS` and `server/src/lib/platformFees.ts`'s `PLANS` — two hand-kept-in-sync records of the same three numbers (rate matches; cap behavior does not, per above). The new entitlement layer is the natural place to collapse this to one definition with one cap semantics applied everywhere fees are computed.
- **Pricing V2** (`PRICING_V2` flag in `server/src/config.ts`, currently **off** in production): a fully-built parallel model — flat 5% fee added on top of the vendor price (not carved out), no tiers, $10/mo per additional seat, $49/mo Featured Vendor placement, 20%-of-fee venue revenue share. Verified correct and tested earlier this session (`pricingMath.ts`, `tests/pricingMath.test.ts`). Has no cap concept at all (by design — the whole point of V2 was removing tiers). **Public marketing already reflects V2** — see §1.7.
- Today, an org can sit on `tier='premier'` (1% fee, no monthly charge ever collected, per §1.4) indefinitely — every fee computation trusts whatever `tier` is stored, and nothing currently keeps that `tier` value honest.

### 1.3a Existing tier-gated features already live — real, reusable patterns, not a blank slate

Two genuine, already-shipped examples of entitlement-style gating exist and are worth holding up as the template for the new centralized service, rather than reinventing the pattern:

- **Contract Pricing Partnerships is Premier-only, enforced server-side, with a clean client contract.** `routes/contracts.ts`: `isPremier(tier) = new Set(["premier","white_label"]).has(tier)`. `POST /api/contract-pricing` and `PATCH /:id/status` return **403** ("Contract pricing partnerships are a Premier feature") for any other tier. `GET /` still lists existing rows read-only but includes a `premier: boolean` flag in the response so the SPA (`src/pages/contracts/ContractPricing.tsx`) can render a full upsell banner ("Premier required," an explanation, and a button that navigates to `/pricing`) instead of the create form when `premier` is false. This is exactly the "server computes the entitlement, client renders around it, never trust a client-side hide" shape the spec's rule 12 asks for — replicate this pattern, don't replace it.
- **Bid-visibility tier windows are a substantial, currently-live marketplace-access entitlement.** `db/bids.ts`'s `canVendorAccessBid()`: in the first 48 hours after a public bid posts, only `premier`-tier vendor orgs may see/act on it; from 48 hours to 7 days, `partner`+`premier`; after 7 days, open to everyone. `client` orgs can never bid. Private/invite-only bids bypass this via an explicit invited-org allowlist. **This entire mechanism is skipped under `PRICING_V2` ("open to all vendors")** — since `PRICING_V2` is off in production today, this tier-gated early-access window is the single largest real entitlement already live in the app, and it's precisely the spec's "more lead-generation capabilities" upgrade trigger, already built. Confirm with the business owner whether this should stay exactly as-is, move into the new centralized entitlement service unchanged, or be reconsidered alongside the V1-vs-V2 decision in §1.7/§7.
- Two smaller tier-linked side effects worth knowing about (not necessarily bugs, just tier having reach beyond the fee rate): `db/profiles.ts`'s public-profile `verified` badge is `true` whenever `tier === 'premier' || tier === 'partner'`, independent of actual verification review status — i.e., today, paying alone grants the "Verified" trust badge. And registration's self-publish gate (`routes/profiles.ts`) lets `partner`/`premier` orgs skip the free-tier's "submit for admin review" step.

### 1.3b Naming: "Plus" and "Pro" already exist in the code, just not everywhere

Three different label sets exist for the same three price points, none of them fully consistent with each other: `server/src/db.ts`'s `TIERS` uses "Free Partner" / "Partner" / "Premier"; `src/pages/GetStarted.tsx`'s client-facing registration tier picker already uses **"Free" / "Plus" / "Pro"** verbatim (`{ key: 'partner', label: 'Plus', price: '$45 / month', fee: '2.5% fee, capped $2,500/event' }`) — i.e. exactly the spec's requested naming, already implemented, just only wired into one screen; and the public Pricing page (§1.7) shows no paid-tier names at all because it markets the tierless V2 model. Recommend standardizing on "Free / Plus / Pro" everywhere a human reads a plan name (reusing `GetStarted.tsx`'s existing copy as the source of truth), while keeping the internal `Tier`/`PlanKey` enum values (`free_partner`/`partner`/`premier`) unchanged in code/DB — a display-label change, not a data-model change.

### 1.3c Role and admin authorization model — flat and duplicated, worth unifying alongside entitlements

- **Two independently-writable "what role is this" columns.** `organizations.type` (free text, no CHECK constraint) and `users.role` (DB CHECK against a 9-value list that is narrower than the 13-value app-level `Role` type in `server/src/db.ts` — `sponsor`/`nonprofit`/`donor`/`volunteer`/`exhibitor`/`viewer` are valid app-level roles but **not** in the `users.role` CHECK constraint, which should be reconciled before role-specific plans are built on top of it, since an inconsistent `users.role` for those roles would make role-based entitlement lookups unreliable). Different server files fall back differently when the two disagree or one is null: `routes/intelligence.ts` uses `user.role ?? org.type ?? "client"`; `db/coo.ts`/`db/command-center.ts`/`db/opportunity.ts` default to `"venue"` instead. Recommend the new entitlement service pick one canonical source (this audit recommends `organizations.type`, since it's what actually drives dashboard routing today) and stop reading `users.role` for anything but the `admin`/`super_admin` sentinel values.
- **Admin authorization is a single flat email allowlist** (`ADMIN_ALLOWED_EMAILS` env var, checked in `computeIsAdmin()`/`requireAdmin`), with no per-org admin, no billing-vs-content permission split, no delegated/scoped admin of any kind — confirmed intentional by an existing internal note ("The WhiteLabelAdmin page self-guards on isAdmin. Do NOT add [more granular checks]"). A **second**, separately-computed admin concept (`users.role IN ('admin','super_admin')`) is checked in parallel via a near-identical inline helper function copy-pasted into roughly 40 different `server/src/db/*.ts` files rather than one shared primitive — several routes explicitly OR both together, confirming both are live simultaneously with no guarantee they stay in sync. Recommend collapsing to one authorization primitive as part of building the centralized entitlement service, since "is this actor allowed to do X" is the same class of question as "does this org's plan include X."
- Minor, adjacent finding worth a one-line fix regardless of this project: `routes/opportunities.ts` reads `req.query.role` (an unauthenticated, client-supplied query parameter) to filter results, rather than deriving role from the authenticated actor.

### 1.4 Stripe / Stripe Connect / checkout (verified in depth earlier this session)

- **No Stripe SDK** — every call is hand-rolled `fetch` against the Stripe REST API (`server/src/lib/processors.ts`, `server/src/lib/stripe-connect.ts`). Deliberate, documented convention throughout this codebase (also true of S3 signing, PayPal).
- **Two parallel, non-overlapping Stripe Connect rails**, both gated on the same `STRIPE_SECRET_KEY`:
  - `lib/processors.ts` + `routes/payments.ts`: vendor/venue invoice payouts. Stripe Checkout Sessions (one-time `mode: "payment"`) for client→vendor payments, with Connect `transfer_data.destination` + `application_fee_amount` for automatic splits when the vendor has completed Connect onboarding. Webhook (`checkout.session.completed`, `account.updated`) verified via HMAC over the raw body, 5-minute replay window, `timingSafeEqual`.
  - `lib/stripe-connect.ts` + `routes/connect-payouts.ts`: a *separate* partner-referral-commission payout rail (`connect_accounts` / `payout_instructions` tables), explicitly documented as "complementary... never touches the partner_payouts ledger."
- `stripeEnabled()` = `!!STRIPE_SECRET_KEY`. Currently unset in this session's environment (real keys not yet provided — the user is adding them "in the meantime" per the prior turn).
- **No Stripe Customer object is created or stored anywhere.** No `stripe_customer_id` column exists on `organizations` or any other table. Every Checkout Session is anonymous (no `customer` param). This matters directly for rule 6 ("do not create duplicate Stripe customers") — there is currently nothing to duplicate *or* reuse; a customer-id column and creation path are new infrastructure.
- **No Stripe Subscription API usage anywhere** (`grep` for `/v1/subscriptions`, `/v1/prices`, `/v1/products` across the whole server returns nothing). Confirmed by tracing all three places that look subscription-shaped:
  - **Tier ($45/$99)**: set once at registration from a client-submitted field, never charged, never re-verified.
  - **Team seats** (`server/src/db/seats.ts`, `routes/seats.ts`, `team_seats` table): `addSeat()` inserts the new seat as `status='active'` — already billable/counted — with **no limit check against `included_seats`/`additional_seats` at all** (those two columns, confirmed by direct inspection, are set once to `1`/`0` at registration and never read anywhere else in the server — effectively dead). `POST /api/seats/checkout` creates, at most, a one-time Checkout Session for the current billable-seat total (only when a processor is configured; otherwise the response literally says "seat billing is tracked and will be charged once payments are enabled" and does nothing). Confirmed the checkout is **entirely decorative even when it succeeds**: the Stripe webhook handler (`routes/payments.ts`) special-cases `event_ticket`/`exhibitor` purposes but has no branch for `kind: "team_seats"`; a completed seat checkout just falls through to a generic payment-ledger record and never touches the `team_seats` table. Net effect: a seat is billable the instant it's added, whether or not checkout is ever clicked, and clicking checkout doesn't change anything about the seat's state either way.
  - **Featured Vendor placement** (`featured_placements` table, Pricing V2 concept): confirmed by reading `buyFeatured()` (`db/featured.ts`) and its route (`routes/featured.ts`) directly — `POST /featured/buy` calls `buyFeatured(orgId, req.body?.processor_ref ?? null)` with **no `createCheckout()` call anywhere in the path**. `processor_ref` is accepted as a raw, unvalidated client-submitted string (or `null`) and stored as-is; the row is marked `active` for a month regardless of what, if anything, was actually paid. This is not "no auto-renewal" (as a first pass at this audit assumed) — it is "no payment is ever collected or verified, under any configuration, full stop."
- **Conclusion**: real recurring billing (Stripe `Customer` + `Subscription` + `Price`/`Product` objects, a Customer Portal or equivalent, subscription lifecycle webhooks driving `organizations.subscription_status`) is **net-new work**, not a reuse-and-wire task. This is almost certainly the largest single piece of Phase 1.

### 1.5 Payments, invoices, quotes, events, itinerary (existing, reusable)

- `events` table: full lifecycle status enum (`inquiry` → ... → `archived`), `organization_id` (owner), `client_id`/`planner_id`, `venue_id`, `required_services`, `event_goals`, `budget`, `guest_count`. This session already extended it with `notify_guests_schedule`.
- `bids`/`quotes`/`invoices`/`payments`: full marketplace transaction pipeline, already fee-aware via `platformFees.ts`/`db/payments.ts`. No changes needed for the entitlement system beyond gating *volume* (see §5).
- `db/itinerary.ts`: derived, role-aware event schedule (`buildItinerary`), already used by this session's automated schedule-distribution feature.
- Messaging (`db/messages.ts`, `routes/messages.ts`): thread-based, event-scoped, visibility-scoped by relationship to the event (`event`, `venue_client`, `vendor_client`, `bid`, `quote`, `invoice`, `direct`, `internal`). Reusable as-is; no plan-gating exists on message volume today.
- Object storage (`lib/objectStorage.ts`, `server/src/storage.ts`): pluggable local-disk/S3, optional AES-256-GCM at rest, HMAC-signed download URLs. No per-org storage quota exists today — this is a listed spec upgrade-trigger ("More storage") that needs new metering.

### 1.6 Feature flags (broken, unrelated to entitlements)

- `src/lib/features.tsx` (`FeaturesProvider`, `useFeatures()`): a **global**, admin-toggleable, role-audience-scoped (`buyer | vendor | both | admin`) boolean flag system, intended for staged feature rollout — not a per-plan entitlement mechanism.
- `getFeatureFlags()` (`src/lib/db.ts`) calls `GET /feature-flags`. **No such route exists anywhere on the server** (`server/src/routes.ts` has no `/feature-flags` mount; no route file defines it). The call 404s, is caught, and `flags` silently resolves to `[]` — every `isOn(key)` call returns `false` for every user, always. `AdminFeatures.tsx` is presumably equally non-functional against this endpoint.
- Not required for this project, but worth fixing incidentally or explicitly deciding to leave broken and build the new entitlement system as a fully separate concept (recommended — do not conflate "is this app feature rolled out yet" with "does this org's plan include this capability").

### 1.7 Public pricing / marketing surface

- `src/pages/public/Pricing.tsx`: explicitly documented in its own header as the **Pricing V2** page — "free for everyone to join... a single flat 5% platform fee... There are no subscription tiers." Three cards today: Clients (free), Venues (free to join + revenue share + $10/mo extra seats), Vendors (free to join + $10/mo extra seats). **No Plus/Pro pricing is shown publicly today at all** — the $45/$99 numbers exist only in backend code and (per the user) internal planning, not on the live marketing site.
- This is a real fork in the road, not a detail: the **live backend enforces the legacy tiered model** (V1, `PRICING_V2=false`), but the **live public page already markets the V2 model** (flat, tierless). A new visitor reads "free, flat 5%" and signs up; the backend then silently assigns them `free_partner` tier (5%, uncapped upgrade path to 2.5%/1% that the page never mentions). This is worth surfacing to the business owner as its own decision, independent of the entitlement build: **does the new 7-role subscription system build price cards on top of the legacy tiers (matching what's actually enforced and what the spec's dollar figures describe), or does it wait for/coordinate with the V2 flip?** This audit assumes the former (legacy tiers, since the spec's exact dollar figures and percentages match `platformFees.ts`'s legacy-tier plan records byte-for-byte) unless directed otherwise.

## 2. What's reusable as-is (do not rebuild)

- `server/src/lib/platformFees.ts` — the fee + cap engine. Extend its `PlanKey`/`PLANS` shape rather than replacing it; also fold in `db/quotes.ts`'s correct per-event cumulative cap logic so there is exactly one cap implementation instead of two (see §1.3).
- Native auth, session signing, `requireUser`/`requireAdmin` middleware.
- **`routes/contracts.ts`'s Premier-gate pattern** (§1.3a) — server returns both the gated resource *and* a boolean flag describing the gate (`{ contracts, premier }`), client renders an upsell using that flag rather than guessing. This is the template for every new entitlement check in Phase 3.
- **`db/bids.ts`'s tier-access-window mechanism** — already does real, live, tier-based marketplace-access gating; fold into the new entitlement service rather than replacing it, pending the §7 decision on V1 vs. V2.
- **`src/pages/GetStarted.tsx`'s tier-picker UI** (cards, pricing, "Plus"/"Pro" copy) — reuse this component's visual pattern for any new plan-selection UI rather than designing a new one; it already has the right shape and, per §1.3b, the right names.
- `organizations` table's existing columns (`tier`, `platform_fee_rate`, `subscription_status`, `billing_contact`) — the right *shape* for a subscription record; they just need a real Stripe-backed lifecycle wired underneath. (`included_seats`/`additional_seats` are the exception — confirmed dead, see §3.)
- Stripe Checkout Session + webhook-HMAC-verification pattern in `lib/processors.ts` — the mechanics (raw-body capture in `app.ts`, signature verification, idempotent recording via `on conflict do nothing`) are correct and battle-tested (verified live this session); the *subscription* variant of Checkout (`mode: "subscription"`) can reuse the same webhook plumbing, adding new event types.
- `db/payments.ts`'s idempotent-insert pattern (`recordProcessorPayment`) — the exact pattern to copy for a new `recordSubscriptionEvent`-style idempotent webhook handler.
- 8 role dashboards' `NavItem[]` pattern — extend with an entitlement check per item rather than replacing the dashboard shell.
- `team_seats` table — reuse for real seat billing once metering/limits are added; do not create a second seats table.
- `featured_placements` table — reuse as the shape for any tier-add-on that needs a `current_period_end`, extend to other add-ons rather than duplicating (but note it currently needs a real payment step added, not just a renewal cron — see §1.4).
- Object storage, messaging, itinerary, quote/bid/invoice systems — untouched by this project except for new usage-metering hooks.

## 3. Gaps (net-new work)

1. **No real recurring billing.** Need: Stripe `Customer` per org (new `stripe_customer_id` column), `Product`/`Price` objects per plan × role (or a shared price set if pricing is role-agnostic beyond Vendor's existing $45/$99), Checkout Session in `mode: "subscription"`, a Customer Portal link (or hand-rolled cancel/upgrade flow), and subscription lifecycle webhooks (`customer.subscription.created/updated/deleted`, `invoice.payment_failed`) driving `organizations.subscription_status` and `tier` automatically. This is the load-bearing piece everything else depends on. Includes fixing Featured Vendor's checkout (currently collects no payment at all, §1.4) and wiring the seat-checkout webhook branch that today does nothing (§1.4).
2. **No multi-org membership.** Need an `organization_memberships` table (user_id, organization_id, role_in_org, status, is_default) alongside — not replacing — `users.organization_id` (kept as the legacy "default org" pointer for backward compatibility with every existing `getActor()` caller). `getActor()` needs a org-switching concept; the SPA's auth context needs a "current org" selector when a user belongs to more than one.
3. **No usage/quota/entitlement service.** Need a single server-side module (e.g. `server/src/lib/entitlements.ts`) that, given an org + capability key, returns the limit and current usage, used by every route that currently has no gate at all (event creation, quote volume, seats — `included_seats`/`additional_seats` are dead columns, not a working limit, see §1 — locations, inventory items, storage bytes, team members, automation runs, integrations).
4. **No per-role plan catalog beyond Vendor.** The spec implies distinct plans/pricing per role (Client, Venue, Vendor — existing $45/$99 — Supplier, Planner, Installer, Sponsor). Only Vendor's plan is priced today. Need a plan catalog table or config keyed by (role, plan_key) rather than the single role-agnostic `TIERS`/`PLANS` records that exist now.
5. **Fee cap is inconsistently enforced** (§1.3) — correct in the quote-generation path, absent from the direct payment-recording path. Needs a single implementation applied everywhere money is priced, before or alongside the entitlement work.
6. **Feature-flag route is dead** (§1.6) — not required by this project, but should not be confused with the new entitlement system; recommend leaving it alone (out of scope) or filing it as a one-line separate fix.
7. **Dual role source and flat/duplicated admin authorization** (§1.3c) — `organizations.type` vs. `users.role` disagree in places; ~40 copy-pasted inline `isAdmin` helpers instead of one shared primitive. Should be unified as part of building the entitlement service, not left to drift further.
8. **`users.role` DB CHECK constraint is narrower than the app-level `Role` type** (§1.3c) — a pre-existing drift, not caused by this project, but worth knowing before extending the role list further.
9. **Public pricing page (§1.7) doesn't mention Plus/Pro at all** and describes a different model than what's enforced. Needs new pricing cards per role once plans are real.
10. **No Stripe Connect Customer ↔ Organization linkage for the *paying* side** — Connect accounts exist for the *receiving* side (vendor/venue payouts) only; a `stripe_customer_id` for the org-as-subscriber is a distinct, currently-absent concept.
11. **Admin Revenue Center's MRR/ARR figures are phantom** — computed purely from self-declared `tier`, unconnected to any real charge (§0). Once real billing exists, this reporting should switch to summing actual Stripe subscription revenue; flag internally in the meantime so nobody makes a business decision off the current number.

## 4. Risks

- **Multi-org membership is the highest-blast-radius change.** Every route that does `getActor()` today implicitly assumes one org. Adding real multi-org support without breaking every existing route means: keep `users.organization_id` as-is (the "default"/"active" org), add the membership table as pure addition, and introduce an explicit "act as org X" mechanism only where the spec's multi-org scenarios actually require it (a session-level "current org" selector is the least invasive approach — same pattern as switching workspaces in most B2B SaaS). Do **not** attempt to migrate every route to a membership-array model in one pass; that is how a "do not break production" project breaks production.
- **Retroactively enforcing tier payment on existing orgs.** Once real billing exists, every org currently sitting on `tier='partner'`/`'premier'` with no Stripe subscription needs a grandfather/reconciliation plan (grace period + downgrade-to-free-if-unpaid, or a one-time backfill charge) — a data/business decision, not a code decision; needs sign-off before the webhook that downgrades lapsed accounts goes live in production. Same question applies to Featured Vendor placements currently marked `active` with no real charge behind them.
- **Two Stripe Connect rails already exist**; a third, subscription-billing-specific Stripe integration surface must not become a fourth uncoordinated rail. Recommend a single new `lib/stripeBilling.ts` (subscriptions only) alongside the existing `lib/processors.ts` (one-time payments) and `lib/stripe-connect.ts` (partner payouts), clearly bounded by comment header the same way the existing two already are.
- **Idempotency**: subscription webhooks (`invoice.paid`, `customer.subscription.updated`) must use the same `on conflict do nothing` idempotent-insert discipline as `recordProcessorPayment` — Stripe retries webhooks, and a naive handler will double-apply a tier change or double-record revenue.
- **Testing without live Stripe keys**: this environment currently has no `STRIPE_SECRET_KEY` (real keys are being added by the user "in the meantime"). Live end-to-end subscription verification (the standard this session has held throughout) needs either the user's test-mode keys or a stub billing server the way this session already stubbed an OpenAI-compatible endpoint for the AI-extraction feature — plan for this in the implementation phase, not as an afterthought.
- **Scope creep risk given the spec's breadth** (7 roles × operating-system modules × entitlements × dashboards × migrations). Phase discipline (§8) is what keeps this shippable instead of stalling in an all-or-nothing rewrite.
- **Changing the bid-access tier windows or the fee-cap enforcement point touches live, revenue-relevant marketplace behavior** (§1.3, §1.3a) — these need explicit sign-off before modification, not just a mention in a migration plan, since they currently affect what real vendor orgs can see and what real transactions are charged today.

## 5. Recommended entitlement model (for review, not yet implemented)

A single centralized service, `server/src/lib/entitlements.ts`, as the spec's rule 5 demands. Sketch (subject to your review before any code is written):

```ts
type CapabilityKey =
  | "events.active" | "quotes.monthly" | "locations" | "inventory_items"
  | "team_seats" | "automation_runs.monthly" | "storage_bytes"
  | "integrations" | "reports.advanced" | "leads.monthly" | ...;

interface PlanEntitlements {
  role: Role;
  planKey: string;          // e.g. "vendor_free" | "vendor_plus" | "venue_pro"
  feeRate: number;          // delegates to platformFees.ts, not duplicated
  feeCapCents: number | null;
  limits: Partial<Record<CapabilityKey, number | null>>; // null = unlimited
}

function getEntitlements(org: DbOrg): PlanEntitlements;
function checkLimit(org: DbOrg, key: CapabilityKey, currentUsage: number): { allowed: boolean; limit: number | null; used: number };
```

Every route that creates a metered resource (new event, new quote, new team seat, new inventory item, ...) calls `checkLimit` server-side before the insert — never a client-side hide alone (spec rule 12). The SPA reads the *same* limits from a `GET /entitlements` endpoint to render upgrade prompts, not to enforce anything.

## 6. Specific code-level findings for the implementation phase

Covered in depth in §1.3c above (dual role source, `users.role` CHECK constraint narrower than the app-level `Role` type, `organizations.type` having no CHECK constraint at all, and the duplicated inline admin-authorization helpers) — not repeated here to avoid drift between two copies of the same finding. Two additional pointers for whoever picks up Phase 1:

- Before adding role-specific plans, verify directly (query the live database, not just the schema) whether `SponsorDashboard`/`NonprofitDashboard` users' `users.role` column actually holds `'sponsor'`/`'nonprofit'` today — the DB CHECK constraint doesn't allow those values, so either the column holds something else for those users (likely `null`, since the `update users set role = $2` at registration would have failed the CHECK) or the constraint has silently drifted from what's in `db/apply-all.sql`. This needs a real query against production before role-based entitlement lookups can trust `users.role` for those two roles.
- `organizations.type` has no CHECK constraint at all (free text) — low-risk, additive to add one when other `organizations` migrations happen in Phase 1, to stop a typo'd role string from being silently accepted at registration.
